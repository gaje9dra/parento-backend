# Phase 7.4 — Backend Monitoring Finalization

## Phase 7 completion status

The backend now has a bounded, authenticated monitoring lifecycle:

Managed Android
→ authenticated device session
→ validated telemetry
→ ownership/enrollment check
→ database-monotonic current state
→ centralized freshness
→ authorized Admin list/detail APIs.

### Implemented

- One authoritative `device_monitoring_state` row per ManagedDevice.
- Schema-versioned telemetry ingestion.
- Device-session authentication for ingestion.
- Server-side device identity derived from the authenticated session; the request cannot choose another ManagedDevice.
- Enrollment/operational-state checks on every ingestion.
- Strict Zod validation and database constraints for supported fields/ranges.
- Client observation timestamps are validated against a bounded future skew.
- Server `receivedAt` is retained separately and used as the authoritative ingestion time.
- Out-of-order and duplicate observations are rejected at the database update boundary.
- Omitted telemetry fields preserve the current value; explicit null clears the field.
- Current state is updated transactionally with ManagedDevice last-seen.
- Admin monitoring list is ownership-filtered in SQL, cursor-paginated, bounded to 100 items, and deterministically ordered.
- Admin detail uses the existing authenticated Admin session and owner predicate.
- Unauthorized device access returns the existing resource-not-found contract rather than confirming ownership.
- Freshness is centralized and calculated consistently from enrollment, communication state, and authoritative observation time.
- Revoked devices report `REVOKED` freshness and cannot ingest telemetry.
- No historical telemetry retention table was introduced; Phase 7 stores current state only.
- Existing Phase 6 realtime boundary remains unchanged and disabled until a secure realtime transport exists.

## Partial telemetry semantics

An omitted field means “not reported in this snapshot” and preserves the previous current value.

An explicit JSON null means “currently unavailable/unknown” and clears that field.

This prevents one unavailable collector from erasing valid unrelated monitoring values.

## Timestamp semantics

`observedAt` is the Managed device's collection timestamp and is used for ordering/freshness only.

`receivedAt` is generated by the backend and is the server-authoritative ingestion timestamp.

Observations more than the configured future-skew allowance are rejected. Old observations are not allowed to overwrite a newer current state.

## Freshness

Default configuration:

- Fresh: less than 5 minutes old.
- Stale: 5 minutes through less than 24 hours.
- Very stale: 24 hours or older.
- Never reported: no current snapshot.
- Offline: communication session is disconnected/expired.
- Revoked: enrollment or operational state is revoked.
- Unknown: no stronger classification is available.

The thresholds are centralized in configuration and used by Admin monitoring responses.

## Database

Migration `0011_phase_7_device_monitoring.sql` adds:

- `device_monitoring_state`
- one-row-per-device primary key
- schema/range/enum constraints
- observation and app-version indexes
- foreign-key cascade for current monitoring state when a device is deleted

No historical telemetry table or retention job was added.

## API

### Managed device

`POST /api/v1/device/monitoring`

Requires an authenticated Phase 6 managed-device session.

The Managed client contract currently stores monitoring snapshots locally and does not yet contain an HTTP monitoring client. The backend contract is therefore documented and ready for that client integration, but no other repository was modified in this phase.

### Admin

`GET /api/v1/admin/devices?limit=&cursor=`

Returns only devices owned by the authenticated Admin.

`GET /api/v1/admin/devices/{deviceId}`

Returns current monitoring information for an owned device. Unauthorized/nonexistent devices are not enumerated.

## Realtime

The existing backend realtime transport is still a not-configured boundary. Phase 7 does not create a second realtime mechanism. Admin clients should use the monitoring APIs and existing safe refresh mechanisms until a secure transport is implemented.

## Security

- Managed telemetry authorization derives device identity from the authenticated session.
- Device status is rechecked at ingestion, so a revoked device cannot continue submitting valid telemetry.
- Admin authorization is enforced before list/detail access.
- Ownership is enforced in SQL rather than client-side filtering.
- Telemetry payloads are bounded by content length and global request limits.
- Telemetry schema and numeric ranges are validated.
- Authorization credentials and tokens are not included in monitoring responses or logs.
- Existing request-id/error conventions are preserved.

## Cross-repository contract

No files were changed in `parento-managed` or `parento-admin`.

The managed repository currently exposes monitoring as a local Room snapshot and its existing `BackendClient` does not yet expose a monitoring synchronization method. Its management-mode enum uses `NOT_MANAGED`; the backend monitoring contract uses `UNMANAGED` to match the Admin monitoring terminology. The future Managed API client must explicitly map these values.

The Admin repository currently has a monitoring UI boundary but its live repository implementation was intentionally left dependency-aware until the backend monitoring contract exists.

## Deferred

- Secure realtime monitoring transport.
- Historical telemetry retention/analytics.
- Direct Managed Android HTTP synchronization implementation.
- Any Phase 8+ sensitive capabilities such as location, camera, microphone, screen capture, blocking, lock/wipe, covert surveillance, or arbitrary remote execution.
